# Seedwell vs qBittorrent 5.2.3: core behaviour parity audit

Date: 2026-10-15. Read-only audit; nothing was built or run. The user's brief: "behavior similar to qBittorrent for the most part, if it makes sense with our additional low memory goal".

Sources
- qBittorrent 5.2.3: a local source checkout of release-5.2.3, `src/base/bittorrent/` (`sessionimpl.cpp` = SI, `torrentimpl.cpp` = TI). Its effective values are the ones set in `SI::loadLTSettings` (SI:1866-2185) and the `SessionImpl` constructor defaults (SI:443-583), which override libtorrent's.
- libtorrent 2.0.11: a local source checkout of libtorrent-rasterbar 2.0.11, `src/` (`settings_pack.cpp` = SP, `session_impl.cpp` = LS, `torrent.cpp` = LT, `announce_entry.cpp` = AE).
- Seedwell: paths relative to the repo root; SPEC = `SPEC.md`.

Constraints that shape every recommendation (do not relax)
- Settled footprint ~40 MB with hundreds of torrents. Finished torrents are Cold (no actor, a record of at most 256 B plus an announce timer; `crates/engine/src/tier.rs:1-12`). Anything that needs an actor per torrent is a memory cost.
- Seedwell paces trackers more strictly than qBittorrent on purpose (SPEC 7B.3, 7C). qBittorrent allows 50 concurrent HTTP announces (SI:493) and re-announces every torrent at once on wake (SI:1700-1712); Seedwell does not and should not. The parallel `stopped` at quit is handled separately.
- User decisions recorded in SPEC: everything resumes on start, staggered, except what the user paused (SPEC §10, `crates/engine/src/session/boot.rs`); flat layout with no templates (SPEC 7A.3); tier-independent announcing (SPEC 7C.4b); private-torrent floor 10 days (SPEC 7B.4a).

Legend: Rec = ADOPT / ADOPT-ADAPTED / KEEP OURS. Effort S (under 1 day), M (1-3 days), L (more). "Mem" = effect on the 40 MB target.

## Headline findings

1. **(Fixed 2026-10-15, SPEC §7C.4c; text below describes the state at the audit.) Seedwell never tells the engine the network changed or the Mac woke.** `Engine::network_changed` (`crates/engine/src/engine.rs:913`) and the whole path below it (`session/settings.rs:199`, `tracker_driver.rs:642`, `hub.rs:671`, `machine.rs:939-966`, `portmap.rs:96`) exist and are tested, but nothing in `app/`, `crates/ffi`, `crates/control` or `crates/cli` calls it. There is no `NWPathMonitor` and no `NSWorkspace.didWakeNotification` observer (`app/Sources/SeedwellApp/App.swift:151-160` only watches power-off, mount and unmount, and mount/unmount only reload settings). There is also no wake input at all: `TrackerHub::wake` (`hub.rs:688`) has no `TrackerCmd` in front of it (`tracker_driver.rs:93` has only `NetworkChanged`). SPEC §5A, §6 and §7C.4 promise this behaviour, so this is a spec gap, not a design choice. With Seedwell's slow seeding backoff (15 min, 30 min, 1 h, 2 h, 4 h, cap 6 h; `crates/tracker/src/backoff.rs:44-49`), a router reboot or a 3-hour Wi-Fi outage can leave every seeding torrent un-announced for another 1 to 5 hours after the network is back.
2. **(Fixed 2026-10-15, Recommendation 3; text describes the audit.) A downloading torrent that has no peers holds a queue slot forever.** `queue::plan` counts every incomplete, unpaused torrent against `max_active_downloads` (`crates/engine/src/queue.rs:23-37`). qBittorrent has the "slow torrents do not count" mechanism; Seedwell has nothing equivalent.
3. **(Fixed 2026-10-15, Recommendation 2; text describes the audit.) Disk-full / permission errors are permanent.** A write failure becomes `Fault{missing:false}` and the torrent stays in `Error` until the user acts (`session/reports.rs:159-168`; only `missing` faults retry, at a flat 60 s, `session/mod.rs:773-785`). libtorrent instead flips to upload mode (keeps seeding) and retries writes every 10 minutes (LT:1117-1133, SP `optimistic_disk_retry` 600 s).
4. **(Fixed 2026-10-15, Recommendation 4; text describes the audit.) No bound on concurrent verification outside the launch stagger.** Adding 30 torrents whose data already exists, or "Recheck all", can run 30 verifications and 30 Hot actors at once. qBittorrent allows one (SI:547, `MaxActiveCheckingTorrents` = 1).
5. **LSD is a setting with no implementation**; `ipv6` is a setting with no IPv6 listener (`crates/engine/src/engine.rs:263` binds an `Ipv4Addr`; `crates/engine/src/config.rs:218`); `crates/ffi/src/settings.rs:476` says `encryption`, `lsd`, `utp` and `ipv6` are not carried by the app settings.

## Recommended changes (prioritised)

Memory is stated per item. Nothing below adds a per-torrent actor to Cold torrents.

1. **Wire network and wake events to the engine. DONE 2026-10-15** (user asked for "a clever mechanism to detect outages and look for restored internet, with minimum cpu, requests"; built as SPEC §7C.4c, which goes further than this recommendation did). The app has `NetworkWatcher.swift` (an event-driven `NWPathMonitor`, debounced 3 s by `PathDebounce`, plus `willSleep` / `didWake`) feeding `Core.networkPathChanged(satisfied:)`, `systemWillSleep()`, `systemDidWake()`. The tracker hub keeps `Online | Offline { since, probe_at }`: it goes Offline on an unsatisfied path or on unreachable-class failures to 2 distinct hosts within 2 minutes with no sign of life elsewhere; while Offline it sends nothing but one probe (the next due announce of one torrent: +30 s, 1, 2, 5 min, then every 5 min), freezes every backoff and rolls back the failures that revealed the outage; on the first answer it releases only the announces that came due, spread over 60 s through the unchanged host gate (no reannounce-everything). Once per recovery the DHT bootstrap backoff resets, zero-peer torrents forget their dial backoff, and the port mapping is refreshed. A wall-clock jump the monotonic clock did not see counts as a wake, which covers the headless daemon (no path monitor there; inference does the rest). Tests: `crates/tracker/tests/outage.rs` (300 torrents, 3 hosts, 5 min and 3 h outages, one dead tracker, unsatisfied path, 10 h sleep, captive portal), `crates/engine/tests/outage.rs`, `crates/dht/tests/core_behaviour.rs`, `PathDebounceTests.swift`. The 3 h soak scenario of the original text is the virtual-clock test, not a real 3 h run.
2. **Make disk errors recoverable. DONE 2026-10-15** (SPEC §5A "Outside conditions"). `trs_storage::StorageError::is_write_blocked` (ENOSPC, EDQUOT, EROFS, EACCES, EPERM) feeds `peer::FaultKind { Other, Missing, Blocked }`, which replaces the old `missing: bool` of `Fault`. A running actor that meets a blocked write goes into upload mode (`Torrent::on_disk_blocked`: no more requests, interest withdrawn, what is verified keeps being served and announced) and reports `DiskBlocked`; a blocked start-up (also "Not enough space") becomes `Error` with the same schedule. New `session/recover.rs`: retries at 10, 20, 40, then every 60 minutes (`DISK_STEPS`), a full disk first checked with `statvfs` (room for `max(4 pieces, 32 MiB)`), the actor restarted from its resume data redialling the peers it had; a fault that returns inside a 5 minute probe window advances the step, one that does not forgets the trouble; the row says "Disk full — retrying in 10 min" (engine text, `TorrentRow::hold_note`, the CLI through `waiting_note`). A torrent in upload mode does not count against `max_active_downloads`. Missing data: the flat 60 s became 1, 5, 15, 60 minutes (`MISSING_STEPS`); `EngineHandle::volumes_changed()` (FFI `Core.volumesChanged()`, called from the `didMount`/`didUnmount` observers in `App.swift`) stats each distinct save folder once off the engine task and flips torrents in bulk (n torrents = one pass, one `replan`): "Drive not connected" for a gone folder, Cold seeds included, and back to work for a returned one, unfinished through the start queue and verifying only what the actor finds it must, behind the gate of Recommendation 4. A finished torrent's timed retry looks at its folder first (one cached `stat`). Memory: three small maps that hold only torrents in trouble. Tests: `crates/engine/tests/recover.rs` (`a_refused_write_waits_and_retries_by_itself` with read-only files, `not_enough_space_is_retried_when_room_appears`, `an_unplugged_drive_is_noticed_in_bulk_and_comes_back_without_rechecks` with 60 torrents, `missing_data_backs_off_instead_of_a_flat_minute`), unit tests in `session/recover.rs` and `storage/src/error.rs`. Not done: the headless daemon has no mount observer (it relies on the retry schedule); a write that fails on a Cold seed's `finalize` move stays a plain error.
3. **Inactive downloads do not hold queue slots. DONE 2026-10-15** (SPEC §7.3). `queue::QueueItem::inactive` and `queue::Stall` (pure, tested with a virtual clock in `queue.rs`): a running download under `stall_rate` (2048 B/s) for `stall_after` (60 s) stops counting, and counts again after 60 s above it (hysteresis both ways; a verifying torrent is never judged). `plan()` gives active downloads their slots first, then lets inactive ones keep running within `TOTAL_FACTOR` (2) x `max_active_downloads`, earliest first, so the memory of the actors stays bounded; `High` and streamed torrents are never held. `session/recover.rs::stall_check` looks at the running downloads every 10 s (only while some run) and calls `replan` when a verdict changes. Row: `TorrentRow::stalled`, text "Stalled — not counted in the queue" (a tracker error wins). The two thresholds are engine constants (`EngineConfig::stall_rate`, `stall_after`), not settings: no Settings control was added. Tests: `queue.rs` (6 new, incl. flicker and cap) and `a_stalled_download_gives_up_its_queue_slot` in `tests/recover.rs`. A side effect worth knowing: with several dead torrents the earliest keeps running as the idle one and the later ones rotate through the counted slot, one actor start per stall period at most.
4. **Global verification slots. DONE 2026-10-15** (SPEC §10 "One verification gate"). `EngineConfig::verify_slots` = 2 (an engine constant, not a user setting; the old `BOOT_MAX_VERIFYING` is gone, the launch stagger and every other path share it). Two layers: (a) `Session::reconcile` keeps a torrent that must hash (`G_UNVERIFIED` or `G_RECHECK`: add with existing data, Recheck, Recheck all, reconnect) in the `BootQueue` with no actor while two are verifying, and `spawn_torrent` marks a new actor as verifying at once so the next decision sees it; (b) `Shared::verify_slots`, a semaphore taken inside `Torrent::startup` around the recheck, is the hard backstop for verifications an actor decides on itself (stale resume data) and is released before the startup slot is held. State "Waiting to verify" (`TorrentState::Checking` + `hold_note`) for waiting ones. `add.rs` was not touched: the gate sits in `reconcile`, which the add path already calls. Diagnostics: `verify_peak`, `replans`. Tests: `at_most_two_torrents_hash_at_once`, `recheck_all_is_gated_too` (one slot, peak 1). Measured with a headless daemon (no LTO build, 48 sparse 1 GiB torrents with 16 KiB pieces, RSS sampled every 50 ms): Recheck all peak 30.5 MB before, 15.6 MB after (idle 9.5 MB); adding the 48 at once peaks at 24.9 / 24.2 MB because that peak is the add-time parsing of 48 torrent files, not the verification; Resume all of 300 paused magnets peaks at 14.0 / 13.3 MB (magnet actors are small, so the saving there is the plan count, not megabytes).
